# ТЗ: Добавление материалов и фурнитуры по ссылке (парсер сайтов)

Статус: **черновик, обсуждён с пользователем, реализация не начата.**
Текущая база: MVP v262. Документ самодостаточен — новую сессию можно
направить сразу на него, без остального контекста переписки, где это
обсуждалось.

## 0. Проблема, которую решаем

Сейчас в панели «Библиотека → Материалы» пользователь может добавить свою
позицию вручную (`libAddRow`/`libAddChildNode` в `src/app.js`) — просто
вписав название/цену/фото руками, без проверки. Сохраняется это только ему
лично, на сервере, в таблице `catalog_overrides` (по `user_id`,
см. `server/src/routes/catalogOverrides.js`) — персонально, не видно другим
пользователям (это отдельный, уже обсуждённый и **отдельно отменённый**
вопрос — эта задача его не включает).

Хотим дать пользователю возможность добавлять позиции **так же, как это
делает разработчик через Claude Code** — по прямой ссылке на товар, с
реальными данными с сайта, а не «на глаз».

## 1. Общий сценарий

1. В панели «Библиотека» — форма «Добавить по ссылке»: выпадающий список
   поддерживаемых сайтов + поле для ссылки на конкретный товар.
2. Список сайтов в выпадающем списке **формируется автоматически** из того,
   для каких сайтов на сервере реально есть парсер — не дублируется
   отдельным хардкодом на клиенте, чтобы список никогда не разошёлся с
   реальностью.
3. Пользователь выбирает сайт, вставляет ссылку, нажимает «Проверить».
4. Сервер открывает именно эту страницу, парсит по правилам выбранного
   сайта: название, цена, единица измерения, размер (для листовых
   материалов — sheetW/sheetH), фото, артикул — что есть на странице.
5. Результат парсинга показывается пользователю **для подтверждения перед
   сохранением** — не сохраняется вслепую (парсинг может ошибиться).
6. Для фурнитуры — см. раздел 3 отдельно, там сложнее.
7. После подтверждения — позиция сохраняется в тот же блок, что и сейчас
   (`catalog_overrides` пользователя), с добавлением `sourceUrl`,
   `sourceSiteId` и даты проверки (`verifiedAt`).
8. Отдельная кнопка **«Обновить цены с сайта»** — одна на весь каталог
   пользователя сразу (не по кнопке на каждую позицию). Перепроверяет по
   сохранённым ссылкам все позиции разом, обновляет цену/название/`verifiedAt`,
   показывает итог (сколько обновлено, что не найдено — например, товар
   сняли с продажи). Никакого автоматического обновления по расписанию —
   только по явному нажатию.

## 2. Сайты на старте

Реализовать парсер для **одного сайта: `mobilier.md`** (это единственный
сайт, который уже используется как источник в `catalog.js`). Архитектура
должна позволять добавлять парсеры под другие сайты позже, не переделывая
форму на клиенте (см. п.1.2 — список сайтов не хардкодить).

## 3. Материалы vs фурнитура — разная сложность

### 3.1. Простые позиции (материалы + простая фурнитура)

Декоры ЛДСП, ХДФ, столешницы, стекло, а из фурнитуры — опоры, крепёж,
штанга, крепление цоколя, полкодержатели. Всё, что нужно, есть на странице
товара: название, цена, размер, артикул. Парсер сайта покрывает это
полностью, дополнительных ручных полей не требуется.

### 3.2. Сложная фурнитура — нужны инженерные параметры, которых нет на странице магазина

Ручки (количество отверстий `holes` + межосевое `cc`), петли (привязка
модели в 3D — `hardwareModelSlot`), подъёмные механизмы (диапазон
применения `minH/maxH/maxW`), ящичные системы — эти параметры **не
публикуются на странице магазина** (там только цена и фото), их берут из
технической документации производителя (присадочные шаблоны и т.п., см.
`ПРАВИЛА-КОНСТРУИРОВАНИЯ.md`, раздел «Правило работы с чертежами
производителя»).

**Решение, согласованное с пользователем: НЕ пытаться автоматически
сопоставлять товар с каталогом производителя и вытаскивать эти параметры
оттуда.** Слишком ненадёжно (чертежи часто в PDF/картинках, риск неверного
распознавания цифры) и слишком высокая цена ошибки (неправильная присадка
портит реальный материал на производстве) — это прямо противоречит
правилу проекта «ни одного невыдуманного числа».

Вместо этого: после парсинга цены/названия форма показывает **дополнительные
поля, которые пользователь заполняет сам** — конкретный набор полей зависит
от категории фурнитуры (`category` в `HARDWARE_PRICES`/`HANDLES`/`LIFTS` и
т.п. в `catalog.js` — ориентироваться на уже существующие там поля по
каждой категории). Без заполнения обязательных инженерных полей позиция не
сохраняется (или сохраняется с явной пометкой «присадка не подтверждена» —
уточнить у furniture-rules при реализации, как это должно вести себя в
движке присадки, чтобы не сломать расчёт).

### 3.3. Категория (подкатегория) для новой позиции, если бренда ещё нет в дереве

Материалы в каталоге организованы деревом категорий с `categoryPath`
(например, `['ДСП', 'Egger']` — тип материала → бренд). Если пользователь
добавляет по ссылке материал/фурнитуру бренда, которого в дереве ещё нет
(например, `GTV`) — программа **предлагает** создать конечную подкатегорию
под этот бренд, а не создаёт её молча:

- Черновой `categoryPath` парсер пытается взять из хлебных крошек страницы
  товара (если у сайта они есть в вёрстке).
- Предложение показывается на том же экране подтверждения, что и
  остальные распознанные поля (см. п.1.5) — пользователь может принять,
  переименовать или выбрать другую категорию из уже существующего дерева
  (переиспользовать `libAddChildNode`/дерево «Библиотеки», не городить
  отдельный механизм).
- Если бренд/категорию с сайта распознать не удалось — предлагать
  сохранить в текущую/общую категорию, не выдумывать название бренда.

## 4. Серверная часть (зона `backend-monetization`, `server/`)

- Новый модуль-парсер под `mobilier.md` (например, `cheerio` для разбора
  HTML) — извлекает название/цену/единицу/размеры/фото/артикул по вёрстке
  конкретно этого сайта.
- `GET /catalog-link-sources` — список поддерживаемых сайтов для
  выпадающего списка на клиенте (id, название, домен) — источник для этого
  списка тот же реестр, что и парсеры (см. п.1.2).
- `POST /catalog-link-parse { siteId, url }` — требует `Authorization:
  Bearer <JWT>` (`requireAuth`, как и текущий `/catalog-overrides`).
  Проверяет, что `url` реально принадлежит домену выбранного `siteId`
  (защита от SSRF — сервер не должен ходить по произвольным ссылкам
  пользователя на что угодно), парсит, возвращает черновик данных **без
  сохранения** — сохранение остаётся отдельным действием через уже
  существующий `PUT /catalog-overrides` (клиент сам добавляет
  подтверждённую позицию в свой блок и отправляет как раньше).
- Батч-эндпоинт для «Обновить цены с сайта» (например, `POST
  /catalog-link-refresh { items: [{ url, siteId }, ...] }`) — перепарсивает
  разом все позиции пользователя, у которых есть `sourceUrl`, возвращает
  обновлённые данные; клиент применяет к своему блоку и сохраняет тем же
  `PUT /catalog-overrides`.
- Разумный таймаut на запрос к внешнему сайту, без следования на сторонние
  домены при редиректах, без хардкод-паролей/токенов — обычный fetch с
  учётом устойчивости (сайт может быть недоступен/изменить вёрстку — тогда
  понятная ошибка клиенту, не 500 с обрывком HTML).
- Гостям (без JWT) фича недоступна — так же, как сейчас недоступны
  личные `catalog_overrides` (см. `scheduleCatalogSave`/`loadCatalogOverrides`
  в `app.js` — гость просто ничего не сохраняет и не грузит).

## 5. Клиентская часть (зона `ui-configurator`, `src/app.js` + `index.html`/`style.css`)

- Форма «Добавить по ссылке» в панели «Библиотека → Материалы» (и там же —
  для фурнитуры, с дополнительными полями по п.3.2).
- Выпадающий список сайтов, подгружаемый с `GET /catalog-link-sources`.
- Клиентская проверка домена вставленной ссылки под выбранный сайт — сразу
  подсказка, если не совпадает, до отправки на сервер.
- Экран подтверждения распознанных данных перед сохранением (поля
  редактируемые — на случай, если парсер прочитал что-то не так).
- Кнопка **«Обновить цены с сайта»** (именно такое название, не «Обновить
  каталог») — одна на весь каталог пользователя.
- Сохранение — через уже существующий механизм (`scheduleCatalogSave`/
  `PUT /catalog-overrides`), просто с двумя новыми полями в объекте позиции:
  `sourceUrl`, `verifiedAt` (плюс `sourceSiteId`, если пригодится для кнопки
  обновления).

## 6. Явно НЕ входит в эту задачу

- Публикация правок какого-либо пользователя (в т.ч. администратора) как
  общего каталога для всех — это отдельная, отменённая пользователем
  задача. Видимость правок остаётся такой же, как сейчас: только у того,
  кто их сохранил.
- Автоматическое сопоставление с каталогом производителя (Blum/Hettich/
  Samet/GTV и т.п.) и автоматическое считывание присадочных параметров
  оттуда — см. п.3.2, решили не делать.
- Автообновление по расписанию (cron) — только вручную по кнопке.
- Поддержка произвольных сайтов вне списка с готовым парсером.

## 7. Делегирование при реализации

| Часть | Субагент |
|---|---|
| Парсер `mobilier.md`, новые эндпоинты, защита от SSRF, батч-обновление | `backend-monetization` |
| Форма в панели «Библиотека», выпадающий список, экран подтверждения, доп. поля для фурнитуры, кнопка «Обновить цены с сайта» | `ui-configurator` |
| Сверка, что поля сложной фурнитуры (holes/cc/hardwareModelSlot/minH-maxH-maxW и т.п.) заведены в форме в том виде, в каком их ожидает движок присадки | `furniture-rules` (сверка, без своего кода — только проверка контракта полей) |
| Проверка после каждого субагента | `code-reviewer` |

После UI-изменений в `src/app.js` (новые вкладки/`id`/способ открытия формы
в «Библиотеке») — прогнать `tools/check.sh` (правило CLAUDE.md о
структурных UI-изменениях), и обновить `tools/smoke.js`/`geometry.js`, если
он покраснеет из-за новой структуры.

Визуальная проверка в браузере обязательна перед тем, как считать задачу
готовой (форма, подтверждение, сохранение — это UI, code-review код не
подтверждает, что это реально работает на экране).

Перед коммитом — как обычно, путь к `index.html` пользователю и его «ок»,
затем коммит и пуш в `master` (см. `CLAUDE.md`).
