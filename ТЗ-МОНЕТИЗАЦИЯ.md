# ТЗ: Монетизация Modul3D

Статус: черновик, согласован с пользователем 2026-08-27. Отражает решения
из обсуждения — не финальная спецификация для разработки, а основа для
детализации перед началом каждого этапа.

Текущая база: MVP v189, чисто клиентское приложение без сборщика и без
сервера (см. `CLAUDE.md`). Монетизация требует добавить серверную часть —
это первый сервер в проекте вообще.

## 1. Разделение функций

| Бесплатно | Платно |
|---|---|
| 3D-конфигуратор, ручной ввод параметров | Экспорт документов: Excel, DXF/CSV, (в будущем) PDF |
| Пресеты готовых модулей | Загрузка эскиза → распознавание ИИ |
| Расчёт и просмотр спецификации/стоимости на экране | |

Расчётное ядро (`engine.js`, `specification.js`) и 3D-вьюер (`viewer.js`)
остаются полностью клиентскими и офлайн — они не меняются.

## 2. Модель оплаты

- **Подписка** (месяц/год) — открывает безлимитный экспорт документов.
- **Токены** — отдельный баланс на аккаунте, списывается только за вызовы
  ИИ-распознавания эскиза (т.к. каждый вызов реально стоит денег в Anthropic
  API — ключ будет привязан к аккаунту разработчика, не пользователя).
- Конкретные цифры (цена подписки, стартовый запас токенов, стоимость
  одного вызова эскиза в токенах) — не зафиксированы, задаются как
  настройки на этапе реализации Этапа 1.

## 3. Приём платежей

- Старт: глобальный приём через Stripe/Paddle (или аналог) — юрлицо/
  подключение не в РФ.
- РФ-приём (ЮKassa/CloudPayments/Тинькофф) — отдельный, более поздний этап,
  т.к. Stripe/Paddle не работают с российскими юрлицами и картами.

## 4. Технический подход к защите платных функций

- **Экспорт документов — жёсткий гейт.** Сейчас `export.js` и `cnc.js`
  генерируют файлы полностью в браузере — код открыт (нет сборщика/
  минификации), клиентскую проверку легко обойти. Решение: параметры модели
  уходят на сервер, файл (.xlsx/.dxf/.csv) генерируется там же и отдаётся
  клиенту только при активной подписке. Логика генерации документов
  переезжает на сервер.
- **ИИ-эскиз — через сервер.** Сейчас `sketchAI.js` вызывает Anthropic API
  прямо из браузера с ключом, который вводит сам пользователь (bring-your-
  own-key). После монетизации: клиент отправляет картинку на свой сервер,
  сервер проверяет баланс токенов пользователя, сам вызывает Claude Vision
  своим ключом, списывает токены, возвращает результат.

### 4.1. Контракт `POST /sketch/recognize` (зафиксировано при реализации Этапа 2)

- Требует `Authorization: Bearer <JWT>` (тот же токен, что выдаёт `/auth/login`).
- Тело запроса — JSON: `{ imageBase64: string, mimeType: 'image/jpeg' | 'image/png' }`
  (без multipart — переиспользует уже существующую на клиенте конвертацию
  файла в base64 из `sketchAI.js`, не тащит на сервер лишнюю зависимость
  вроде multer).
- Списание токенов — **atomic conditional decrement**, чтобы закрыть гонку
  при параллельных запросах:
  1. `UPDATE token_balances SET balance = balance - $cost WHERE user_id = $1
     AND balance >= $cost RETURNING balance` — если 0 строк, баланс
     недостаточен, сразу `402` до обращения к Anthropic.
  2. Только после успешного списания — вызов Anthropic Vision.
  3. Если вызов Anthropic упал (сеть/API/невалидный JSON в ответе) — токены
     возвращаются обратно (`balance = balance + $cost`), клиенту — ошибка,
     явно указывающая, что токены не списаны.
  4. При успехе — в ответе клиенту отдаётся актуальный остаток токенов.
- Стоимость одного распознавания в токенах — `SKETCH_TOKEN_COST` (env,
  дефолт `1`), не хардкодить.
- Промпт и функция `sanitizeRecognizedParams` (зажатие размеров в
  разумные для мебели пределы) переезжают на сервер **без изменений** — это
  уже провалидированные мебельные значения, не переизобретать заново.

### 4.2. Минимальный вход в аккаунт — перенесён в Этап 2

Изначально экран входа планировался в Этапе 4 («UI оплаты»), но без него
токены физически не к чему привязать — ИИ-эскиз не может работать анонимно.
Поэтому в Этап 2 включён **минимальный** вход/регистрация (email + пароль,
JWT в localStorage, отображение остатка токенов рядом с загрузкой эскиза).
Полноценный UI подписки/оплаты документов — по-прежнему Этап 4, на этой же
основе (не дублировать, а достраивать).

### 4.3. Контракт Этапа 3 — жёсткий гейт на документы (зафиксировано при реализации)

Важно: на сервер переезжает только **формирование файла** (xlsx/dxf/csv),
не пересчёт геометрии. `engine.js` остаётся единственным источником истины
и не портируется на сервер — клиент по-прежнему сам считает `model.parts`/
`spec` (как сейчас), а на сервер отправляет уже готовые данные вместе с
`Authorization: Bearer <jwt>`. Сервер проверяет подписку и только формирует
файл из присланных данных — геометрию не пересчитывает и не проверяет (это
не задача гейта: подделывать свои же размеры пользователю незачем).

Роуты (`server/src/routes/export.js`), все требуют активную подписку
(`subscription.status` — `active` или `trialing`; иначе `402`):

- `POST /export/detailing` — body `{ model, projectName }` → `.xlsx`
- `POST /export/specification` — body `{ spec, projectName }` → `.xlsx`
- `POST /export/cnc/csv` — body `{ model }` → `.csv`
- `POST /export/cnc/dxf` — body `{ model }` → `.dxf`

Ответ — сырое тело файла (не JSON) с корректными `Content-Type` и
`Content-Disposition: attachment; filename="..."`, клиент оборачивает в
`Blob` и скачивает как раньше. Коды ошибок: `401` — не авторизован, `402` —
нет активной подписки, `400` — некорректное тело запроса.

Логика формирования содержимого (колонки, форматы, единицы измерения)
переносится в `server/src/services/exportGeneration.js` **без изменений** —
это зона `export-cutting`, даже когда код физически на сервере (см.
`.claude/agents/backend-monetization.md`, раздел «Что НЕ твоя зона»).
`backend-monetization` отвечает только за роуты и проверку подписки
(`server/src/middleware/subscription.js` — новый мидлвар, по аналогии с
`requireAuth`).

### 4.4. UX ошибок доступа — не коды, а понятный призыв к действию

Пользователю **никогда** не должен показываться голый код ошибки (401/402)
или техническое сообщение вроде «Ошибка сервера». Вместо этого:

- **Не вошёл в аккаунт** → сообщение + кнопка, которая открывает уже
  существующую панель «Аккаунт» (сделана в Этапе 2) на форме входа/
  регистрации.
- **Вошёл, но нет активной подписки** → сообщение + кнопка **«Оформить
  подписку»**, которая по решению пользователя должна быть рабочей уже
  сейчас (не заглушкой) — вызывает `POST /billing/checkout` (готов с Этапа
  1) и:
  - если сервер вернул `checkoutUrl` — переход по нему;
  - если `checkoutUrl: null` — открыть оверлей Paddle.js:
    `Paddle.Checkout.open({ transactionId })`.

  Для оверлея на клиенте нужно подключить Paddle.js (проверено по
  официальной документации, не выдумано):
  ```html
  <script src="https://cdn.paddle.com/paddle/v2/paddle.js"></script>
  <script>
    Paddle.Environment.set('sandbox'); // 'production' в бою
    Paddle.Initialize({ token: 'PADDLE_CLIENT_TOKEN' }); // публичный клиентский токен, не секретный ключ сервера
  </script>
  ```
  `PADDLE_CLIENT_TOKEN` — публичный клиентский токен из Paddle Dashboard →
  Developer Tools → Authentication → Client-side tokens (начинается с
  `test_`/`live_`, безопасен для клиентского кода — это НЕ тот секретный
  `PADDLE_API_KEY`, что на сервере). Константа в клиентском коде, как
  `API_BASE` в `sketchAI.js` — с комментарием, что для боя нужно заменить
  на `live_...` токен и `Environment.set('production')`.

Этот пункт частично затрагивает и уже сделанную в Этапе 2 панель
«Аккаунт» — расширяем её, а не дублируем.

## 5. Этапы реализации

1. **Аккаунты + бэкенд + платежи** — регистрация/вход, хранение статуса
   подписки и баланса токенов в БД, интеграция Stripe/Paddle.
2. **ИИ-эскиз через сервер** — прокси-эндпоинт с ключом Anthropic на
   сервере, списание токенов за вызов, перенос логики из `sketchAI.js`.
3. **Жёсткий гейт на документы** — перенос генерации из `export.js`/
   `cnc.js` на сервер, выдача файла только при активной подписке.
4. **UI оплаты** — экран входа, индикатор подписки и остатка токенов, окно
   оплаты/пополнения (правки в `app.js`/`ui-shell.js`, `index.html`).
5. **Проверка** — `code-reviewer` по каждому этапу, ручной прогон сценариев
   в браузере (без подписки/токенов — платные функции недоступны; с
   оплатой — доступны). Формулы конструктора не затрагиваются, поэтому
   `tools/smoke.js` не требуется, если Этап 1–4 не трогает `engine.js`.
